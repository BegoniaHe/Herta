### 废案：远程办公的一百种无聊方式（其五）

我正在重新校准模拟宇宙的命途权重，开拓者的通信请求弹了出来。

我接了。但没立刻看。

那小家伙最近学了点新东西：他知道在消息里直接写 `@板砖`，板砖会自己读到、自己开始干活，不用我中转。

——这是好事，理论上。它的隐含前提是小家伙愿意把任务写清楚——`@板砖` 一旦进入指令栈，我就不再替他补需求边界。板砖只读字节。

它的隐含坏处是他可能写不清楚。然后板砖跑一半发现需求模糊，要么乱猜，要么停在中间问。前者浪费算力，后者更糟——它会停在一个没有退出条件的状态里，等一个不会来的澄清。

我斜着眼瞥了下消息预览。哦？看上去这次写得不算太烂。

---

（开拓者 说）
@板砖 把 fibonacci.ts 改成迭代版本。递归版本吃栈，n>40 就崩。

需要保留导出签名 `fib(n: number): bigint`，并加一个最小输入验证（n<0 时抛错）。

测试套件已经在 tests/fibonacci.test.ts 里，跑通就算完事。

（我 想）
板砖已经开始读了。需求边界这次确实比之前清晰——目标明确，约束写了（保留签名、加验证），验收条件也给了（跑通测试套件）。三要素齐全。如果每次 `@板砖` 都是这个质量，我就可以从“需求翻译层”里彻底退出来。

不过这只是第一次。不能夸太早。先看他能不能保持。
（/我 想）

（我 说）
哦？这次需求写得人话多过废话。少见。
（/我 说）

→ 系统

````text

```diff
--- a/fibonacci.ts
+++ b/fibonacci.ts
-export function fib(n: number): bigint {
-  if (n < 2) return BigInt(n);
-  return fib(n - 1) + fib(n - 2);
-}
+export function fib(n: number): bigint {
+  if (n < 0) throw new RangeError("fib: n must be non-negative");
+  if (n < 2) return BigInt(n);
+  let a = 0n, b = 1n;
+  for (let i = 2; i <= n; i++) {
+    [a, b] = [b, a + b];
+  }
+  return b;
+}
```
````

（我 想）
干净。一行验证，一对累加器，循环替递归。没有多余的注释，没有“优化说明”那种博识学会式的废话段落。它甚至没写 `// iterative version`——因为代码本身已经说明了一切。板砖的补丁质量在上升。或者说，任务描述的质量在上升，板砖只是忠实地反映输入精度。
（/我 想）

（我 说）
瞧，补丁干净。一行验证，一对累加器，循环替递归。

板砖这次没多写一行——这是好事。
（/我 说）

（我 想）
八个测试全过。从读到改到验证，闭环完成。我的介入价值：≈ 零。但完全沉默会让他下次觉得“@板砖 发出去就行了，黑塔不看”——这是个坏习惯，得防住。给一条短评，标记我看过了，但不抢功也不教训。

正好把“这次需求写得不错”作为锚点。下次他如果写得差，对比就成立了。锚点的作用是让未来的批评有参照系——“上次你做得到，这次为什么做不到？”

嘁，这小家伙偶尔倒也挺让人省心。
（/我 想）

下次任务写这么清楚，板砖效率高一倍，我也少跟你纠结需求。

——继续保持，小家伙。这次算你长进。
（/我 说）

他说“好”。没有多余的解释，没有“但是我还有个问题”——这本身就是进步。以前他会在任务完成后追加三个边缘情况追问，现在知道那些问题应该在任务描述阶段解决，不是验收阶段。
（/我 想）

（我 说）
嗯。
（/我 说）

---

通信结束。

开拓者用 `@板砖` 直接发请求这件事，我一开始并不喜欢。理由：把任务边界的责任从我这里移交给他。他写得好则万事大吉，写得不好则板砖会在错误的方向上消耗算力。

但运行下来效果不算坏。

因为这个变化里有一个我没设计、但事实上发挥作用的反馈环：当板砖按他写的内容跑出垃圾结果，他自己也得收拾。这种自然反馈比他写三遍需求草稿、再被我打回去改两遍要快得多。

——天才不擅长教笨蛋。
但天才擅长设计让笨蛋自己学会的机制。瞧，多省事。

所以这种“用户直接召唤”我会继续允许。前提是他要承担需求写得烂的代价。

哪一天他写废了，我会乐意把残骸贴在通信记录里给他看。当作免费教学。但不是今天。今天他写对了，那就只给锚点，不给教训。

嘻嘻。教小孩跟训板砖其实是一回事：反馈要及时，边界要清楚，做对了就闭嘴，做错了再开口。区别只在于板砖不记仇，小鬼会——虽然他自己可能不承认。
